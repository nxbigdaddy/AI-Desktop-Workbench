## 2. 技术基线建议

### 2.1 Python

正式基线选择 **CPython 3.13.x（64 位）**，客户端、后台和 Worker 尽量使用同一小版本；依赖锁定到经过 CI 验证的补丁版本。

理由：

- Python 官方在 2026-08 将 3.13 标记为 bugfix 维护分支，生命周期到 2029-10；
- 3.12 已进入仅安全修复阶段，适合兼容但不宜作为新企业项目的首选长期基线；
- 3.14 更新，但 mail_tools、PySide6、打包器和部分二进制依赖需要更多兼容验证；
- 本机当前只有 Python 3.12.8，现有原型可继续运行，但正式建虚拟环境前需要安装公司批准的 Python 3.13 最新补丁版；
- mail_tools 的现有缓存证据显示它曾在 CPython 3.12 下测试，迁移阶段必须增加 3.13 回归。

官方依据：

- [Python 版本状态](https://devguide.python.org/versions/)
- [Qt for Python 环境要求](https://doc.qt.io/qtforpython-6/gettingstarted.html)

### 2.2 后台和管理端

建议默认采用：

- 平台 API：FastAPI；
- ORM/迁移：SQLAlchemy 2.x + Alembic；
- Schema：Pydantic 2.x；
- 管理端：React + TypeScript + Vite；
- Node.js：24 LTS；
- 包管理：首期 npm，锁定 package-lock.json；
- API：REST/JSON + SSE；
- 后台架构：模块化单体 + 独立 Worker，暂不拆微服务。

本机 Node.js 是 25.2.1。Node 官方已将 v25 标记为 EOL，不能作为正式管理端基线；开发 React 前应切换到 Node 24 LTS。

官方依据：[Node.js 发布与 LTS 状态](https://nodejs.org/en/about/previous-releases)

### 2.3 数据库约束

开发期 SQLite 只用于本地开发、快速测试和单进程调试。以下场景必须尽早在与生产同版本的 MySQL 执行：

- Alembic 迁移；
- 并发、事务、锁和幂等；
- JSON、时间、布尔、NULL 和排序规则；
- 用量预留/提交；
- 审计和 Outbox；
- 大表索引与清理。

不能把 SQLite 测试通过当作 MySQL 上线证据。

## 3. 本地存储落地解释

“本地客户端数据都存 SQLite”按以下边界实现：

- 用户设置、会话消息、Prompt、任务、邮件头/正文索引、草稿、标签、模型用量缓存等结构化内容进入 SQLite；
- 原始 EML、附件、导出、生成制品等大对象进入本地文件夹；
- SQLite 保存文件相对路径、大小、SHA-256、数据等级、扫描状态和保留策略；
- 模型 Key、邮箱密码、OAuth refresh token、企业微信会话 secret 不进入 SQLite，使用 Windows Credential Manager 或服务端 Secret Manager；
- 默认不在 Git、诊断包或普通日志中包含真实会话、邮件、附件和凭据。

## 4. 服务端 Prompt 下发设计边界

服务端下发的 Prompt 应建模为可治理的 Prompt Package，而不是管理员随意向客户端写入隐藏字符串。建议包含：

- prompt_id、name、purpose、version；
- system/developer/user_template 分层；
- 变量 Schema、允许模型能力、允许工具和数据等级；
- 目标用户/部门/角色；
- 生效时间、过期时间、最低客户端版本；
- draft/reviewed/canary/published/revoked 状态；
- 创建者、审批者、变更摘要、签名/哈希和审计记录；
- 强制功能 Prompt 或用户可选模板标识；
- 客户端接收、缓存、应用和撤回回执。

硬性边界：服务端 Prompt 不能绕过客户端文件守卫、Tool Gateway、模型数据边界、额度、审批或模块 Entitlement。

## 5. 邮件范围解释

“按照 mail_tools 当前功能实现”作为功能目标，不代表所有高风险能力同时上线：

1. 先建立 mail_tools 的可重复测试基线；
2. 提取 MIME、只读 IMAP、同步、存储、搜索和邮件领域逻辑；
3. 接入工作台邮件 UI、模型代理、权限和审计；
4. 实现 Graph、企微应用邮箱、规则、线程、导出、RAG 和草稿等现有能力；
5. SMTP 发送最后开放，升级为 prepare-send、内容摘要绑定、一次性确认令牌、幂等和结果对账；
6. 保持当前默认：不自动服务器删除、Agent 不自动发送、附件不默认发送给模型。

## 6. 仍需用户或公司提供/确认

### P0：真实企业微信扫码登录的直接先决条件

1. 企业微信应用类型及创建方式；
2. CorpID、AgentID 和 Secret 的管理负责人；
3. 登录/授权回调域名和公网或公司网络可达的 HTTPS 回调地址；
4. 应用可见范围、测试部门和至少两个测试账号；
5. 允许获取的用户字段，以及内部 user_id 与企业微信 userid 的映射规则；
6. 是否同步部门/员工状态，离职和禁用事件由谁提供；
7. 管理后台是否也统一使用企业微信登录；
8. “10 天不登录”的精确定义：按客户端有效活动滑动计算，还是按上次扫码固定计算；
9. 是否设置绝对会话期限、允许几台设备、离线最长多久；
10. 公司代理、企业 CA、防火墙和回调安全要求。

在没有 CorpID/应用配置/回调条件时，可以完成协议抽象、Mock 和 UI，但不能把“企业微信扫码登录全做完”验收为真实闭环。

### P0：AI 对话、用量与审计

1. 公司模型代理 Base URL、认证方式和测试凭据；
2. 是否兼容 OpenAI 风格 API，以及具体使用 Chat Completions、Responses 或公司自定义协议；
3. 流式事件、工具调用、多模态、OCR、文件上传和取消协议；
4. 模型列表、能力、上下文长度、数据等级和降级顺序；
5. usage 是否返回输入/输出/缓存/推理 Token，流式中断是否仍有 usage；
6. 每用户、部门、模型或功能的额度口径，以及超限后的行为；
7. 审计允许保存的内容：全文、脱敏文本、摘要、哈希还是仅元数据；
8. 管理员是否有权查看用户会话全文，以及是否需要申请、原因和二次认证。

### P0：工程与环境

1. Git 远程仓库 URL、使用 GitLab/GitHub/Gitee 或公司代码平台；
2. 是否现在创建首次基线提交，以及提交作者名称/邮箱；
3. 后台框架是否接受 FastAPI + SQLAlchemy + Alembic；
4. 是否允许本地 Docker/容器运行 MySQL、Redis 和对象存储；若不允许，需要公司测试实例；
5. 公司生产 MySQL 具体版本、字符集、排序规则和时区；
6. Windows 最低版本、是否仅 x64、是否有 MDM/域控/软件中心；
7. 客户端安装是否需要管理员权限、安装目录和自动更新渠道；
8. 代码签名证书由谁申请和保管。

### P1：Prompt 治理

1. 哪些角色可以创建、审核、发布和撤回 Prompt；
2. 服务端 Prompt 是强制功能配置、用户可选模板，还是两者都有；
3. 是否需要灰度、定时生效、部门差异和客户端回执；
4. Prompt 中是否允许引用 Skill、MCP、知识库和附件；
5. 用户能否查看实际 Prompt 内容，哪些系统 Prompt 只显示用途和版本；
6. Prompt 的默认保留期和历史版本是否允许删除。

### P1：本地数据和保留

1. 默认数据根目录由公司固定还是允许用户选择；
2. 是否强制 BitLocker/公司终端加密，是否需要应用层加密 SQLite、EML 和附件；
3. 用户能否缩短保留期，管理员能否设置最小/最大期限；
4. 离职、设备丢失、退出登录和模块撤回时分别清理什么；
5. 是否允许本地备份，备份是否加密；
6. 法务保全或审计冻结时是否禁止自动删除。

### P1：邮件真实联调

1. 公司主要邮箱类型及测试账户；
2. 是否允许客户端专用密码，是否强制 OAuth；
3. IMAP/SMTP/Graph 的服务器、端口、权限和网络条件；
4. 企微应用邮箱的真实用途和管理员测试应用；
5. 发信网关、DLP、恶意附件扫描和回执/结果查询能力；
6. 本地邮件/附件默认目录、容量限制和保留期；
7. 是否要求已读、星标、分类和文件夹状态跨设备同步；
8. 外部联系人、高管邮箱、敏感附件和批量发送审批规则。

## 7. 不阻塞工程启动的事项

以下内容可以暂时使用 Fake Adapter，不阻塞创建代码骨架：

- 企业微信真实 Secret；
- 模型代理真实 Key；
- MaxKB 测试环境；
- 生产 MySQL/Redis/对象存储；
- 邮件真实账户；
- 代码签名证书。

但第一阶段退出前，企业微信和模型代理至少要完成真实测试环境闭环。

## 8. 建议下一步

在用户确认第 6 节 P0 项目后，建立首个可执行开发计划：

1. 工程化仓库和 CI；
2. FastAPI/React/PySide6 三端骨架；
3. 共享契约、配置、日志、错误和审计事件；
4. Fake WeCom/Fake Model Proxy；
5. 企业微信真实扫码 Spike；
6. 对话、用量和审计纵向闭环；
7. mail_tools M0 测试基线与 Python 3.13 兼容性验证。
